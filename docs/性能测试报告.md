# IM Linux服务端性能测试报告

## 测试结论

在VMware Ubuntu 24.04本机回环环境中，服务端完成5000个并发TCP长连接与持续心跳测试，共处理299536次请求与响应，响应成功率100%，吞吐量9662.17响应/秒，P99延迟28.066 ms。测试期间没有连接失败、异常断线、协议错误、写失败、业务队列拒绝或任务积压。

## 测试环境与范围

- 服务端：C++17、Linux `epoll` ET、非阻塞I/O、4个业务工作线程。
- 数据库：MySQL连接池大小为4；本次心跳协议不执行SQL，因此结果不代表数据库业务吞吐量。
- 压测端：Python 3 `asyncio`，与服务端运行在同一台VMware虚拟机。
- 网络：`127.0.0.1:56789` 本机回环，不包含物理网络延迟、丢包和带宽限制。
- 构建类型：Release。
- 协议帧：4字节网络序长度加4字节心跳协议号，共8字节。
- 请求模式：每批发送2帧，10%的写入随机拆分为1至7字节，用于覆盖粘包和半包场景。

> 当前未记录虚拟机CPU、内存和宿主机配置。正式投递简历前，建议补充硬件配置，并增加跨主机与数据库业务压测。

| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 5 / 5 | 100% | 1.00 | 0.755 ms | 1.129 ms | 1.129 ms | 1.500 ms |
| 100 | 6000 / 6000 | 100% | 199.56 | 4.523 ms | 8.517 ms | 10.617 ms | 13.069 ms |
| 1000 | 60000 / 60000 | 100% | 1984.55 | 3.562 ms | 8.875 ms | 28.123 ms | 72.471 ms |

5000连接测试的理论上限为300000次请求。实际少464次，是因为压测持续时间包含连接逐步建立阶段，较晚建立的连接发送批次更少；已发送的299536次请求全部收到响应，不属于服务端丢包。

## 服务端指标核对

5000连接测试期间的服务端指标快照显示：

- 累计接受连接5000，快照时活动连接5000。
- 接收147400个协议包、1179200字节，平均每包恰好8字节。
- 发送147400个协议包、1179200字节，收发数量完全一致。
- 待处理业务任务为0，累计拒绝任务为0。
- 数据库获取超时和数据库失败均为0。

服务端快照是每30秒采集一次，因此147400是采样时刻的中间累计值，而压测报告中的299536是测试结束后的完整统计，两者统计时点不同。

## 数据库业务冒烟测试

使用10对独立账号完成登录、好友校验、消息持久化、离线补发和消息ACK的端到端测试：

| 指标 | 结果 |
| --- | ---: |
| 发送者登录 | 10 / 10 |
| 接收者登录 | 10 / 10 |
| 消息持久化 | 50 / 50 |
| 离线消息补发 | 50 / 50 |
| 消息ACK | 50 / 50 |
| 登录、连接、持久化、协议及任务失败 | 0 |
| 消息持久化吞吐量 | 628.00条/秒 |
| 离线补发吞吐量 | 2943.45条/秒 |
| 持久化平均延迟 | 11.764 ms |
| 持久化P95 / P99延迟 | 15.007 / 15.804 ms |
| 接收者登录平均延迟 | 8.640 ms |

这组结果证明数据库业务链路功能正确。持久化阶段仅持续0.080秒、补发阶段仅持续0.017秒，样本时间过短，628.00条/秒和2943.45条/秒暂不作为稳定性能结论；正式业务基线以更大规模测试为准。

### 100对账号业务基线

100对独立账号、每对100条消息的测试结果：

| 指标 | 结果 |
| --- | ---: |
| 发送者登录 | 100 / 100 |
| 接收者登录 | 100 / 100 |
| 本轮消息持久化 | 10000 / 10000 |
| 本轮离线消息补发 | 10000 / 10000 |
| ACK发送 | 10000 |
| 登录、连接、持久化、协议及任务失败 | 0 |
| 消息持久化吞吐量 | 1130.18条/秒 |
| 离线补发吞吐量 | 15174.63条/秒 |
| 持久化平均 / P95 / P99延迟 | 43.730 / 53.318 / 58.963 ms |
| 接收者登录平均 / P95 / P99延迟 | 116.544 / 231.508 / 244.313 ms |

清理历史测试消息并重新构建后复测，本轮10000条消息与10000个ACK数量完全一致，所有客户端错误计数为0。服务端共接受并关闭200条连接，执行41600次数据库操作，数据库连接池超时和失败均为0，业务任务积压和拒绝均为0。

测试还暴露出客户端发送最后一批ACK后立即关闭时的尾包处理窗口：旧实现遇到 `EPOLLRDHUP` 会先关闭连接并丢弃尚未调度的完整包。Reactor现已改为先读尽并拆包，再将断线清理排在连接任务队尾。

修复后的服务端收包指标与协议计算完全一致：200个登录帧、10000个聊天请求和10000个ACK合计20200包、82248000字节；200个登录响应、400个用户信息、10000个聊天响应和10000个离线消息合计20600包、82464000字节。数据库查询确认本轮10000条消息的 `delivered_at` 全部已更新，待确认数量为0，证明正常关闭时的尾部ACK不会再丢失。

## 复现命令

```bash
ulimit -n 65535

python3 tests/load_test.py \
  --host 127.0.0.1 \
  --connections 5000 \
  --duration 30 \
  --burst 2 \
  --fragment-ratio 0.1 \
  --output report-5000.json
```

测试时可用以下命令核对服务端指标：

```bash
grep '"event":"server_metrics"' server-5000.log | tail -n 3
```

## 简历表述建议

基于Linux `epoll` ET、非阻塞I/O、业务线程池和`eventfd`跨线程唤醒实现Reactor IM服务端，支持半包粘包处理、连接内有序执行、慢客户端保护及有界任务队列；在VMware回环心跳压测中支撑5000个并发TCP长连接，达到9662响应/秒、100%响应成功率和28.1 ms P99延迟。
