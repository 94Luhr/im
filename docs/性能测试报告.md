# IM Linux服务端性能测试报告

## 测试结论

在VMware Ubuntu 24.04本机回环环境中，服务端完成5000个并发TCP长连接与持续心跳测试，共处理299536次请求与响应，响应成功率100%，吞吐量9662.17响应/秒，P99延迟28.066 ms。Windows到VMware跨主机环境中，服务端稳定维持5000个连接，完整处理148514次心跳请求，成功率100%，吞吐量4901.94响应/秒，P99延迟60.599 ms。两项最终基线均无连接失败、异常断开、协议错误或写失败。

## 测试环境与范围

- 服务端：C++17、Linux `epoll` ET、非阻塞I/O、4个业务工作线程。
- 虚拟机：2个vCPU、5.7 GiB内存、3.5 GiB交换空间；宿主CPU为Intel Core i9-13900H，虚拟化平台为VMware。
- 数据库：MySQL连接池大小为4；本次心跳协议不执行SQL，因此结果不代表数据库业务吞吐量。
- 压测端：Python 3 `asyncio`，与服务端运行在同一台VMware虚拟机。
- 网络：`127.0.0.1:56789` 本机回环，不包含物理网络延迟、丢包和带宽限制。
- 构建类型：Release。
- 协议帧：4字节网络序长度加4字节心跳协议号，共8字节。
- 请求模式：每批发送2帧，10%的写入随机拆分为1至7字节，用于覆盖粘包和半包场景。

硬件明细保存在 `docs/results/vm-hardware.txt`。本机回环用于测量Reactor处理能力，跨主机测试用于覆盖Windows宿主机到Linux虚拟机的实际网络路径，两者不能直接横向比较延迟。

## 服务端指标核对

5000连接测试期间的服务端指标快照显示：

- 累计接受连接5000，快照时活动连接5000。
- 接收147400个协议包、1179200字节，平均每包恰好8字节。
- 发送147400个协议包、1179200字节，收发数量完全一致。
- 待处理业务任务为0，累计拒绝任务为0。
- 数据库获取超时和数据库失败均为0。

服务端快照是每30秒采集一次，因此147400是采样时刻的中间累计值，而压测报告中的299536是测试结束后的完整统计，两者统计时点不同。

压测端运行于Windows宿主机，服务端运行于地址 `192.168.111.128` 的VMware Ubuntu虚拟机。最终5000连接测试先完成全部连接尝试，再将首轮心跳发送均匀摊开到1秒内；每连接每秒发送1帧，10%的写入继续随机拆分以覆盖TCP半包。

5000连接报告的实际压测耗时为30.297秒，总耗时31.000秒。连接失败、异常断开、协议错误和写失败均为0，证明跨主机长连接与心跳链路稳定。由于首轮发送错峰以及Python定时调度边界，请求数略低于理论150000次；所有实际发送请求均收到响应。

服务端最终指标与客户端报告逐项一致：累计接受并关闭5000个连接，接收和发送均为148514包、1188112字节，测试结束后活动连接与待处理任务均为0，业务队列拒绝为0，`accept_fd_limit_paused` 告警为0。

### 文件描述符限制故障与修复

首次完整窗口复测时，服务端进程没有继承另一个Shell执行的 `ulimit -n 65535`，活动连接数停留在约1012。监听队列中的连接等待接近30秒，随后出现146次业务队列保护性拒绝。日志连续打印 `accept4: Too many open files` 并增长到约892 MB。

最终测试在服务端启动Shell中设置65535文件描述符上限后通过。Reactor同时新增fd耗尽退避：遇到 `EMFILE/ENFILE` 时暂时从epoll移除监听socket，在连接释放fd后自动恢复，并对告警限频，避免资源耗尽时形成忙循环和日志洪泛。

使用10对独立账号完成登录、好友校验、消息持久化、离线补发和消息ACK的端到端测试：

| 接收者登录 | 10 / 10 |
| 消息持久化 | 50 / 50 |
| 离线消息补发 | 50 / 50 |
| 消息ACK | 50 / 50 |
| 登录、连接、持久化、协议及任务失败 | 0 |
| 消息持久化吞吐量 | 628.00条/秒 |
| 离线补发吞吐量 | 2943.45条/秒 |
| 持久化平均延迟 | 11.764 ms |

这组结果证明数据库业务链路功能正确。持久化阶段仅持续0.080秒、补发阶段仅持续0.017秒，样本时间过短，628.00条/秒和2943.45条/秒暂不作为稳定性能结论；正式业务基线以更大规模测试为准。

清理历史测试消息并重新构建后复测，本轮10000条消息与10000个ACK数量完全一致，所有客户端错误计数为0。服务端共接受并关闭200条连接，执行41600次数据库操作，数据库连接池超时和失败均为0，业务任务积压和拒绝均为0。

测试还暴露出客户端发送最后一批ACK后立即关闭时的尾包处理窗口：旧实现遇到 `EPOLLRDHUP` 会先关闭连接并丢弃尚未调度的完整包。Reactor现已改为先读尽并拆包，再将断线清理排在连接任务队尾。

修复后的服务端收包指标与协议计算完全一致：200个登录帧、10000个聊天请求和10000个ACK合计20200包、82248000字节；200个登录响应、400个用户信息、10000个聊天响应和10000个离线消息合计20600包、82464000字节。数据库查询确认本轮10000条消息的 `delivered_at` 全部已更新，待确认数量为0，证明正常关闭时的尾部ACK不会再丢失。

## 复现命令

```bash
cd /mnt/hgfs/linuxgongxiang/imServer
ulimit -n 65535

python3 tests/load_test.py \
  --host 127.0.0.1 \
  --connections 5000 \
  --duration 30 \
  --burst 2 \
  --fragment-ratio 0.1 \
  --output report-5000.json
```

跨主机最终基线在Windows PowerShell执行：

```powershell
python tests\load_test.py `
  --host 192.168.111.128 `
  --connections 5000 `
  --duration 30 `
  --interval 1 `
  --burst 1 `
  --fragment-ratio 0.1 `
  --startup-spread 1 `
  --output docs\results\cross-host-5000-final.json
```

服务端的 `ulimit` 必须与启动命令位于同一个Shell，可通过 `/proc/<pid>/limits` 核对进程实际继承值。大规模测试日志应写入Linux本地磁盘，避免VMware共享目录I/O干扰结果。

测试时可用以下命令核对服务端指标：

```bash
grep '"event":"server_metrics"' server-5000.log | tail -n 3
```

## 简历表述建议

基于Linux `epoll` ET、非阻塞I/O、业务线程池和`eventfd`跨线程唤醒实现Reactor IM服务端，支持半包粘包处理、连接内有序执行、慢客户端保护、有界任务队列及fd耗尽退避；在2核、5.7 GiB VMware环境中支撑5000个并发TCP长连接，本机回环达到9662响应/秒和28.1 ms P99延迟，Windows跨主机测试达到4902响应/秒和60.6 ms P99延迟，两项响应成功率均为100%。
